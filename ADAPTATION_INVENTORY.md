# Adaptation Inventory

This file lists the Guix-specific adaptations that Qubes reviewers are most
likely to inspect.  It is not a substitute for reading the code; it is a map of
where behavior intentionally diverges from stock Qubes VM agent packaging.

## Package Build Adaptations

| Area | Code location | Adaptation | Rationale | Current validation |
| --- | --- | --- | --- | --- |
| QubesDB daemon supervision | `qubesdb-vm`, phase `run-vm-daemon-in-foreground` | Prevent `db-daemon` from forking when built without systemd. | Shepherd supervises the child it starts; daemonizing hides the real daemon and can leave duplicate QubesDB daemons racing for the same vchan. | Guix module load, rootfs build/inspection snapshot, and nested-dom0 TemplateVM/AppVM QubesDB smoke evidence exist; the final signed release branch still needs fresh validation. |
| qrexec login shell paths | `qubes-vm-qrexec`, phase `support-guix-login-shell-paths` | Increase qrexec-agent environment buffer from 64 bytes to `PATH_MAX`. | Guix login shells live under `/gnu/store/...`, which can exceed the upstream short buffer. | Guix module load and prior rootfs activation evidence; live qrexec smoke remains a release gate. |
| qrexec PAM selection | `qubes-vm-qrexec`, `build` and `install` phases | Pass upstream `HAVE_PAM_APPL=1` instead of patching PAM detection. | The upstream Makefile probes `/usr/include`; Guix inputs are not exposed there during the build. | Build smoke on GCP and activation tests check qrexec PAM materialization. |
| qrexec wait service | `qubes-vm-qrexec`, `install` phase | Replace `qubes.WaitForSession` with a Shepherd-compatible check for qrexec fork-server readiness. | Upstream waits for systemd user-session state; native Guix uses Shepherd. | Activation tests cover the RPC wrapper, and nested-dom0/openQA smoke covers `qubes.WaitForSession`; the final signed release branch still needs fresh validation. |
| qrexec Python path and FHS layout | `qubes-vm-qrexec`, `install` phase Python block | Move `/usr/*` payloads into profile-visible `/bin`, `/lib`, `/share`, copy qrexec Python modules, and patch generated Python entry points. | Qubes installs to FHS paths, while Guix profiles expose package outputs without merging `/usr`. | Rootfs inspection, activation evidence, and nested-dom0 TemplateVM/AppVM qrexec smoke exist; the final signed release branch still needs fresh validation. |
| `/etc/skel` home initialization | `qubes-vm-core`, phase `dereference-guix-skel-in-home-init` | Resolve `/etc/skel` before `cp -a -T`. | Guix exposes `/etc/skel` as a generated store symlink; preserving the symlink would make new user homes point at immutable store state. | Activation tests cover `/etc/skel` materialization. |
| Core agent version propagation | `qubes-vm-core`, build phase | Derive package metadata and upstream `VERSION=` arguments from `%qubes-source-components`. | Avoid silent drift between pinned Qubes tags and package/build metadata. | Guix module-load checks assert package object versions against the pinned table under real Guix; release builds still require full rootfs/RPM/runtime validation. |
| Core agent post-install hooks | `qubes-vm-core`, `install` phase Python block | Add profile-visible `PATH`, force `qubes.PostInstall` as root, add Guix updates proxy forwarder, preserve supported-service feature reporting without systemd, add Python paths, and install `qubes-firewall`/`qubes-vmexec` wrappers. | Qubes post-install hooks and feature reporting assume FHS paths and systemd. Native Guix needs the same Qubes-visible behavior through Shepherd/profile paths. The updates proxy wrapper uses the current Qubes `qrexec-client-vm --use-stdin-socket '' qubes.UpdatesProxy` form because the Shepherd service hands each TCP connection to `socat EXEC:`, which provides the child a stream socket on standard input/output. | Activation tests cover `qubes.PostInstall`; nested-dom0/openQA evidence covers postinstall diagnostics and update-proxy service state for current artifacts; final signed release validation and real Guix update downloads remain open. |
| GUI agent generated configure scripts | `qubes-vm-gui`, phase `patch-generated-configure-invocation` | Invoke generated `configure` scripts with `CONFIG_SHELL` and avoid the top-level generated configure path that conflicts with Guix shebang patching. | Generated autotools files can retain shell assumptions that fail after Guix patches shebangs. | GCP rootfs build evidence; GUI openQA remains a release gate. |
| GUI startup under Guix | `qubes-vm-gui`, `install` phase | Install profile hooks, adjust `qubes-run-xorg`, provide Xorg module path, run root-owned xinit/Xorg while keeping the session command under the default user. | The upstream non-GuiVM path expects distro Xorg/logind integration; the Guix image uses profile paths and does not provide that wrapper stack. | Nested-dom0/openQA smoke covers basic GUI and appmenu behavior; the final signed release branch still needs fresh validation and broader GUI testing. |
| GUI FHS normalization | `qubes-vm-gui`, `install` phase | Move `/usr/bin`, `/usr/lib`, `/usr/share`, `/usr/include` into profile-visible output paths and repair Qubes RPC symlinks. | Qubes GUI agent installs into distribution FHS paths; Guix activation links `/usr` compatibility paths back to the system profile. | Rootfs inspection and nested-dom0/openQA appmenu smoke evidence exist; the final signed release branch still needs fresh validation. |
| Xorg driver runpaths | `qubes-vm-gui`, phase `set-xorg-driver-runpath` | Add runtime library paths to built Xorg drivers. | Guix does not rely on a global dynamic linker path for package outputs. | Rootfs inspection and basic GUI smoke evidence exist; the final signed release branch still needs fresh validation. |

## System Activation and Service Adaptations

| Area | Code location | Adaptation | Rationale | Current validation |
| --- | --- | --- | --- | --- |
| Qubes compatibility paths | `qubes-vm-compat-service-type` | Create `/usr/bin`, `/usr/sbin`, `/usr/share`, `/usr/lib/qubes`, `/etc/qubes-rpc`, `/run/qubes*`, `/var/run/qubes*`, `/bin`, and `/sbin/poweroff` compatibility links into the current system profile and runtime directories. | Qubes VM agents and RPC services use stable FHS paths; Guix package outputs live under immutable store paths exposed through profiles. | Activation tests cover key generated paths, and nested-dom0 TemplateVM/AppVM smoke evidence exists for both variants; the final signed release branch still needs fresh validation. |
| Mutable `/etc/fstab` | `qubes-vm-compat-service-type` | Materialize `/etc/fstab` if Guix exposes it as a store symlink. | Qubes `mount-dirs.sh` appends private-volume entries at runtime. | Activation tests and rootfs inspection. |
| Qubes PAM services | `qubes-qrexec-pam-service-type` | Provide PAM services through Guix `pam-root-service-type`. | Keeps PAM declarative instead of mutating `/etc/pam.d` in package phases. | Activation tests check qrexec PAM files. |
| QubesDB and qrexec services | `qubes-db-service-type`, `qubes-qrexec-agent-service-type` | Run QubesDB and qrexec through Shepherd with Qubes runtime environment variables and device setup. | Native Guix uses Shepherd; Qubes agents still need Xen device permissions and Qubes runtime paths. | Nested-dom0 TemplateVM/AppVM qrexec and QubesDB smoke evidence exists for both variants; final release branch still needs fresh validation. |
| qrexec fork server | `qubes-qrexec-fork-server-service-type` and GUI package autostart path | Keep qrexec fork-server aligned with GUI session readiness. | It daemonizes and is part of the Qubes GUI session readiness path, not a simple long-running Shepherd child. | Nested-dom0/openQA smoke covers qrexec and session readiness; the final signed release branch still needs fresh validation. |
| meminfo writer | `qubes-meminfo-writer-service-type` | Supervise Qubes `meminfo-writer` through Shepherd, honoring `/run/qubes-service/meminfo-writer` and standard threshold/delay defaults. | Matches Qubes guest-side memory ballooning plumbing without systemd. | Nested-dom0 AppVM smoke verifies the service flag, pidfile, live process, and `pgrep -x meminfo-writer`; `scripts/test-memory-balloon-dom0.sh` also passed with the AppVM growing from 400 MiB to 698 MiB under pressure. |
| updates proxy | `qubes-updates-proxy-forwarder-service-type`, `qubes-guix-update-proxy-service-type`, `guix-service-type`, and core agent wrapper | Forward Guix traffic through Qubes `qubes.UpdatesProxy`; configure Guix tooling to consume the local Qubes proxy; do not implement a separate updater policy. | Keeps network/update behavior inside the Qubes RPC model. Shepherd provides the local TCP listener via `socat`, while the per-connection wrapper follows Qubes' current socket-activated `--use-stdin-socket` command to preserve bidirectional EOF handling. The Guix daemon proxy is set declaratively through `guix-configuration` so boot does not restart `guix-daemon`; a Guix-specific service generates a `/run/qubes/bin/guix` wrapper plus `/etc/profile.d` PATH hook for client-side Guix commands after `qubes-sysinit`. | Controlled nested-dom0 smoke verifies forwarding to a temporary dom0 `qubes.UpdatesProxy` target, the 2026051602 nested-dom0 run verifies default `@type:TemplateVM -> @default target=sys-net` forwarding through stock Qubes policy, and RPM-mode openQA job 27 verifies the generated Guix daemon/client proxy configuration plus service state for rebuilt `guix-minimal`. Real Guix update-tooling downloads through that proxy remain a release gate. |
| private volume layout | `qubes-mount-dirs-service-type`, `qubes-bind-dirs-service-type`, system `swap-devices` | Use standard `/dev/xvdb -> /rw`, `/rw/home -> /home`, `/rw/usrlocal -> /usr/local`, and `/dev/xvdc1` swap. | Matches the standard Qubes template storage model while expressing it declaratively in Guix. | Nested-dom0 AppVM smoke verifies `/rw`, `/home`, `/usr/local`, home persistence, `/dev/xvdb`, `/dev/xvdc1`, and active `/proc/swaps` entry; final release branch still needs fresh validation. |

## Review Notes

- The adaptations above should remain small and Guix-specific.  If an upstream
  Qubes release removes the need for one, drop the local adaptation rather than
  carrying it forward.
- Source-changing substitutions are intentionally named by phase.  If Qubes
  maintainers prefer patch files, the source-edit rows above are the conversion
  candidates.
- `VALIDATION.md` is the source of truth for which adaptations have live
  TemplateVM/AppVM evidence and which are still only build/rootfs/module-load
  evidence.
