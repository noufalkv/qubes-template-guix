# Adaptation Inventory

This file lists the Guix-specific adaptations that Qubes reviewers are most
likely to inspect.  It is not a substitute for reading the code; it is a map of
where behavior intentionally diverges from stock Qubes VM agent packaging.
The validation column points at the relevant gate; `VALIDATION.md` is the source
of truth for current evidence.

## Package Build Adaptations

| Area | Code location | Adaptation | Rationale | Validation path |
| --- | --- | --- | --- | --- |
| Xen vchan runtime subset | `xen-vchan-libs` package | Copy only the Xen shared libraries needed by VM-side vchan/qrexec components and rewrite copied-library RPATHs to that reduced output. | The full Guix Xen package also retains hypervisor tools, QEMU, firmware, and OVMF that are not part of a Qubes TemplateVM guest runtime.  The template only needs the VM-side vchan library closure, while dom0 supplies the hypervisor and VM kernel. | Validate with rootfs builds, image inspections, and dom0/openQA qrexec/QubesDB smoke from the submitted source. |
| Package-time test policy | Qubes VM packages with `#:tests? #f` | Disable package-time tests only where the selected upstream subdirectory has no test target or where upstream tests require a live Qubes/Xen/systemd/GUI environment. | A Guix package build container does not provide QubesDB, qrexec, Xen devices, systemd, or a Qubes GUI session.  The reviewable test story should use artifact and runtime gates instead of text-only substitutes. | Validate package artifact shape with Builder/RPM checks, generated guest state with rootfs activation, and Qubes behavior with dom0/openQA gates. |
| VM-side component package split | `qubes-libvchan-xen`, `qubes-linux-utils-qrexec`, `qubes-vm-utils`, and `qubesdb-vm` build/install phases | Build selected VM-side upstream targets and install them with explicit `PREFIX`, `LIBDIR`, `BINDIR`, include, and Python `site-packages` paths: vchan, `linux-utils/qrexec-lib`, `linux-utils/qmemman`, and QubesDB daemon/client/bindings. | Qubes upstream repositories are normally assembled by RPM/Deb packaging specs that also carry distribution service files and host-side policy.  Native Guix packages need small, declarative guest-runtime outputs without importing distro package scripts as hidden policy. | Validate with rootfs builds for the derivations and dom0/openQA smoke for QubesDB, qrexec, meminfo-writer, and memory ballooning. |
| QubesDB daemon supervision | `qubesdb-vm`, phase `run-vm-daemon-in-foreground` | Prevent `db-daemon` from forking when built without systemd. | Shepherd supervises the child it starts; daemonizing hides the real daemon and can leave duplicate QubesDB daemons racing for the same vchan. | Validate with rootfs inspection and dom0/openQA QubesDB smoke. |
| qrexec login shell paths | `qubes-vm-qrexec`, phase `support-guix-login-shell-paths` | Increase qrexec-agent environment buffer from 64 bytes to `PATH_MAX`. | Guix login shells live under `/gnu/store/...`, which can exceed the upstream short buffer. | Validate with rootfs activation and dom0/openQA qrexec smoke. |
| qrexec PAM selection | `qubes-vm-qrexec`, `build` and `install` phases | Pass upstream `HAVE_PAM_APPL=1` instead of patching PAM detection. | The upstream Makefile probes `/usr/include`; Guix inputs are not exposed there during the build. | Validate with a Guix build plus activation checks for qrexec PAM materialization. |
| qrexec wait service | `qubes-vm-qrexec`, `install` phase | Replace `qubes.WaitForSession` with a Shepherd-compatible check for qrexec fork-server readiness. | Upstream waits for systemd user-session state; native Guix uses Shepherd. | Validate with activation checks for the RPC wrapper and dom0/openQA `qubes.WaitForSession` smoke. |
| qrexec Python path and FHS layout | `qubes-vm-qrexec`, `install` phase Python block | Move `/usr/*` payloads into profile-visible `/bin`, `/lib`, `/share`, copy qrexec Python modules, and patch generated Python entry points. | Qubes installs to FHS paths, while Guix profiles expose package outputs without merging `/usr`. | Validate with rootfs inspection, activation, and dom0/openQA qrexec smoke. |
| `/etc/skel` home initialization | `qubes-vm-core`, phase `normalize-guix-skel-in-home-init` | Resolve `/etc/skel` before `cp -a -T`. | Guix exposes `/etc/skel` as a generated store symlink; preserving the symlink would make new user homes point at immutable store state. | Validate with activation checks for `/etc/skel` materialization. |
| Core agent version propagation | `qubes-vm-core`, build phase | Derive package metadata and upstream `VERSION=` arguments from `%qubes-source-components`. | Avoid silent drift between pinned Qubes tags and package/build metadata. | Validate upstream tag freshness with `scripts/check-qubes-pins.sh`; release builds still require full rootfs/RPM/runtime validation. |
| Core agent packaging payloads | `qubes-vm-core`, `install` phase | Install upstream `qubes-rpc`, `network`, `misc`, `app-menu`, and `filesystem` payloads in addition to `install-corevm`. | Qubes RPM/Deb packaging installs some VM payloads outside the upstream `install-corevm` target.  Native Guix packaging still needs the network setup helpers, feature-reporting hooks, appmenu sync helpers, filesystem snippets, and `/usr/share/qubes/marker-vm` expected by Qubes post-install and Template Manager flows. | Validate with rootfs inspection, RPM-mode openQA postinstall checks, network-uplink service checks, appmenu smoke, and qvm-template lifecycle. |
| Core agent post-install hooks | `qubes-vm-core`, `install` phase Python block | Add profile-visible `PATH`, force `qubes.PostInstall` as root, add Guix updates proxy forwarder, preserve supported-service feature reporting without systemd, add Python paths, and install `qubes-firewall`/`qubes-vmexec` wrappers. | Qubes post-install hooks and feature reporting assume FHS paths and systemd. Native Guix needs the same Qubes-visible behavior through Shepherd/profile paths. The updates proxy wrapper uses the current Qubes `qrexec-client-vm --use-stdin-socket '' qubes.UpdatesProxy` form because the Shepherd service hands each TCP connection to `socat EXEC:`, which provides the child a stream socket on standard input/output. | Validate with activation checks for `qubes.PostInstall`, dom0/openQA postinstall diagnostics, update-proxy service checks, and a real Guix update download. |
| GUI agent generated configure scripts | `qubes-vm-gui`, phase `patch-generated-configure-invocation` | Invoke generated `configure` scripts with `CONFIG_SHELL` and avoid the top-level generated configure path that conflicts with Guix shebang patching. | Generated autotools files can retain shell assumptions that fail after Guix patches shebangs. | Validate with rootfs builds and RPM-mode openQA GUI/appmenu smoke. |
| GUI agent build subset | `qubes-vm-gui`, `build` phase | Build the GUI agent, runuser helper, common Xorg library, and Qubes Xorg input/video drivers; the PipeWire audio module is built and packaged separately as `pipewire-qubes` instead of inside this GUI package. | Keeping the X11 GUI agent and the PipeWire audio module in separate packages matches their separate runtime responsibilities (display forwarding versus audio), keeps the GUI package focused, and lets the minimal variant include the GUI agent without pulling in PipeWire. | Validate basic GUI/appmenu behavior with dom0/openQA; audio is covered by the separate `pipewire-qubes` adaptation below. |
| Qubes PipeWire audio module | `pipewire-qubes` package, `%qubes-normal-audio-packages` | Build `libpipewire-module-qubes.so` from the pinned `qubes-gui-agent-linux` source against Guix `pipewire`, `qubes-libvchan-xen`, and `qubesdb-vm`; install it plus the `30_qubes.conf` drop-in into the profile's PipeWire module and config directories; ship an `etc/xdg/autostart/qubes-pipewire.desktop` entry (and `qubes-pipewire-start` launcher) that starts `pipewire`, `pipewire-pulse`, and `wireplumber` in the per-user GUI session; and add `pipewire`, `wireplumber`, and `pipewire-qubes` only to the normal variant. | Qubes 4.3 audio uses a VM-side PipeWire module that bridges to the AudioVM over vchan.  Upstream loads it through `systemd --user`, which this Shepherd-only template does not have, so the daemons are started through the same XDG autostart path the GUI agent already uses for qrexec-fork-server (run by `qubes-session-autostart`), keeping audio self-contained in its own package instead of editing the GUI agent.  PipeWire and the module install under the same profile subdirectories, so PipeWire's default config search merges the drop-in and resolves the module by name.  The minimal template, like Qubes' own minimal templates, omits audio. | Validate with rootfs inspection for the installed module/drop-in/autostart entry, and dom0/openQA audio smoke (PipeWire loads `libpipewire-module-qubes` and opens the AudioVM vchans). |
| GUI startup under Guix | `qubes-vm-gui`, `install` phase | Install profile hooks, adjust `qubes-run-xorg`, provide Xorg module path, run root-owned xinit/Xorg while keeping the session command under the default user, and make the temporary root-owned Xorg/user-session split explicit with `-ac`. | The upstream non-GuiVM path expects distro Xorg/logind integration; the Guix image uses profile paths and does not provide that wrapper stack or a distro xauth handoff for a root-owned Xorg server to authorize the default user's session client.  The `-ac` flag is therefore review-sensitive compatibility state, not something to hide as ordinary GUI setup. | Validate with dom0/openQA GUI/appmenu smoke and broader GUI/security review, including whether a narrower xauth/logind-style handoff can replace `-ac`. |
| GUI FHS normalization | `qubes-vm-gui`, `install` phase | Move `/usr/bin`, `/usr/lib`, `/usr/share`, `/usr/include` into profile-visible output paths and repair Qubes RPC symlinks. | Qubes GUI agent installs into distribution FHS paths; Guix activation links `/usr` compatibility paths back to the system profile. | Validate with rootfs inspection and dom0/openQA appmenu smoke. |
| Xorg driver runpaths | `qubes-vm-gui`, phase `set-xorg-driver-runpath` | Add runtime library paths to built Xorg drivers. | Guix does not rely on a global dynamic linker path for package outputs. | Validate with rootfs inspection and GUI smoke. |

## Image Build and Reconfiguration Adaptations

| Area | Code location | Adaptation | Rationale | Validation path |
| --- | --- | --- | --- | --- |
| Default root image size | `scripts/build-native-rootfs.sh` | Use a 20G default root image, matching the current Qubes Builder v2 `template-root-size` default used by standard Fedora/Debian template entries unless a release config overrides it, instead of shrinking the release image default to the Guix closure size. | Keeps TemplateVM volume sizing aligned with Qubes template expectations and avoids making Guix a special small-root case that reviewers and users have to account for separately. | Release evidence should record normal and minimal 20G root image builds, Builder-shaped root image builds, and RPM-mode openQA.  The local RPM contract checks intentionally use tiny generated images only for fast package-layout checks, not as release-size evidence. |
| Installed reconfiguration inputs | `.guix-channel`, `modules/qubes/packages.scm`, `config/qubes-system.tmpl`, `scripts/render-config.sh`, `scripts/build-native-rootfs.sh`, `config/channels.scm`, installed `/etc/config.scm`, and `/etc/qubes-guix-channel` | Treat this repository as a Guix channel for Qubes VM package/service definitions.  `config/qubes-system.tmpl` is the operating-system template; `scripts/render-config.sh` substitutes the variant and the rootfs builder installs the rendered file as `/etc/config.scm`.  The builder requires `config/channels.scm`, runs authenticated `guix pull -p <temporary-profile> --allow-downgrades -C config/channels.scm` against Guix's official Codeberg channel URL, builds with `guix system -L <repo>`, and installs the channel module into the image.  The Guix pin is not installed as user/root Guix state. | A single template rendered per variant keeps one source of truth for the operating-system form and bakes the variant into the installed `/etc/config.scm` instead of a runtime environment variable or marker file.  `/etc/config.scm` imports the installed channel module, so reconfiguration does not depend on a builder checkout.  Release-quality image builds still start from a recorded Guix channel, while normal `guix pull` state remains user/root owned and unpinned by the image. | Validate with rootfs inspection, activation, and a live `guix system -L /etc/qubes-guix-channel/modules reconfigure --no-bootloader --allow-downgrades /etc/config.scm` from the installed template. |
| Generated `/sbin/init` entrypoint | `scripts/build-native-rootfs.sh` | Write a small `/sbin/init` wrapper that uses the installed Guix system profile shell, prepares `/proc`, `/sys`, `/dev`, `/run/qubes`, `/run/qubes-service`, and `/var/run` compatibility paths, exports `GUIX_NEW_SYSTEM=/var/guix/profiles/system`, and then executes the Guix system boot program. | Qubes dom0 boots the template with its own kernel and expects `/sbin/init` in the guest root.  `guix system init --no-bootloader` installs the Guix system profile and boot program, but the Qubes boot path still needs a stable guest entrypoint and early runtime directories before Shepherd starts Qubes services. | Validate with `scripts/inspect-native-rootfs.sh` and actual TemplateVM/AppVM boots under openQA or dom0 smoke. |
| Template Manager RPM payload | `scripts/package-native-template-rpm.sh`, `scripts/builder-v2-template-adapter.sh build-rpm`, `tests/template-rpm-payload-check.sh`, `builder-v2-template/appmenus*.list`, and `scripts/template-appmenus.sh` | Package the root image as split `root.img.part.NN` tar payloads, copy the shared `template.conf` with PVH/qrexec/GUI metadata, generate the three Qubes appmenu allowlists from one variant list, include appmenu directories and `clean-volatile.img.tar`, mark `private.img` and `volatile.img` as RPM ghosts, and make `%pre` reject direct `rpm`/`dnf` installation. | Qubes templates are installed through `qvm-template`, not by ordinary package-manager installation.  The RPM should expose the Template Manager payload and metadata contract while leaving private and volatile images managed by Qubes.  Keeping one allowlist source per variant and one shared `template.conf` avoids hand-maintained duplicate metadata. | Validate with the RPM contract checks, payload reassembly, and dom0 qvm-template lifecycle install/reinstall/remove/upgrade/downgrade runs. |

## System Definition Adaptations

| Area | Code location | Adaptation | Rationale | Validation path |
| --- | --- | --- | --- | --- |
| Dom0-provided kernel | `qubes-dom0-kernel-bootloader`, system `bootloader`, `kernel`, `initrd-modules`, and `kernel-arguments` | Use a no-op bootloader record and a placeholder kernel package while building root images with `--no-bootloader`; keep an empty guest initrd module list and Qubes-style `console=hvc0`/`panic=1` kernel arguments; the generated bootloader config still references the Guix boot entry so `guix system init` keeps the full system closure reachable. | Qubes dom0 supplies the VM kernel; a native TemplateVM image should not pull in or install a guest bootloader stack, but the Guix image build still needs a complete system closure copied into the target root and the booted VM should use the expected Qubes console/panic behavior. | Validate with rootfs builds, inspections, and openQA or dom0 TemplateVM/AppVM boots. |
| Lean Guix base services | `%qubes-base-services`, `%qubes-omitted-base-service-types`, `%qubes-minimal-base-services`, `%qubes-sysctl-service`, and system `services` | Keep Guix base services needed by the image; omit the default console/login/network/sysctl service set, then add only the needed login and `hvc0` agetty services explicitly; keep `guix-daemon` usable for ordinary AppVM networking instead of forcing it through an inactive localhost update proxy; provide Qubes-owned loopback/network/sysctl services; and add DBus explicitly for GUI/session tooling. | Qubes provides kernel, device, and network lifecycle through VM agents; the template should not start unrelated virtual consoles or independent network policy, but the Qubes serial console still needs a usable login prompt.  The Qubes updates-proxy forwarder is still present for update-client VMs, while update operations that must use it supply the proxy environment explicitly. | Validate with rootfs activation, dom0/openQA smoke, generated proxy configuration, hvc0 console login, and real Internet Guix update downloads. |
| Default Qubes user and privilege policy | system `users`, `groups`, `privileged-programs`, and `sudoers-file` | Provide the standard `user` account in `wheel` plus Qubes-related groups, keep Guix default setuid programs, add Qubes' `qfile-unpacker` through Guix privileged-program handling, and enable Qubes-style passwordless sudo. | Matches standard Qubes template defaults instead of inventing a Guix-specific login or sudo policy; Qubes file-copy RPC needs the unpacker to run with the intended privilege even though Guix store outputs themselves are not trusted as privileged executables. | Validate with rootfs activation and dom0/openQA smoke as the expected default user. |
| Normal/minimal package and appmenu split | `modules/qubes/packages.scm`, `config/qubes-system.tmpl`, `scripts/template-variant.sh`, `scripts/render-config.sh`, `qubes-variant-packages`, `qubes-host-name`, `xterm-desktop-entry` | Keep both variants GUI-capable with `xterm.desktop`; add `xfce4-terminal`, `thunar`, `mousepad`, `evince`, and Qubes audio (`pipewire`, `wireplumber`, `pipewire-qubes`) for the normal template; the template's `@VARIANT@` token selects `qubes-variant-packages`/`qubes-host-name`, and `scripts/template-variant.sh` keeps variant names and expected command lists in one helper for build/openQA/lifecycle scripts. | Mirrors the Qubes normal/minimal template expectation while making the normal template expose a basic discoverable desktop app surface and working audio instead of only Qubes generic wrappers; the minimal variant stays small, audio-less, and visible to appmenu discovery.  The variant is chosen at render time, not at runtime. | Root image inspection, RPM layout checks, and RPM-mode openQA should cover variant-specific command, desktop, and audio entries. |

## System Activation and Service Adaptations

| Area | Code location | Adaptation | Rationale | Validation path |
| --- | --- | --- | --- | --- |
| Qubes compatibility paths | `qubes-vm-compat-service-type` | Create `/usr/bin`, `/usr/sbin`, `/usr/share`, `/usr/lib/qubes`, `/etc/qubes-rpc`, `/run/qubes*`, `/var/run/qubes*`, `/bin`, and `/sbin/poweroff` compatibility links into the current system profile and runtime directories. | Qubes VM agents and RPC services use stable FHS paths; Guix package outputs live under immutable store paths exposed through profiles. | Validate with activation checks for generated paths plus dom0/openQA smoke for both variants. |
| Mutable `/etc/fstab` | `qubes-vm-compat-service-type` | Materialize `/etc/fstab` if Guix exposes it as a store symlink. | Qubes `mount-dirs.sh` appends private-volume entries at runtime. | Validate with activation checks and rootfs inspection. |
| Qubes PAM services | `qubes-qrexec-pam-service-type` | Provide PAM services through Guix `pam-root-service-type`. | Keeps PAM declarative instead of mutating `/etc/pam.d` in package phases. | Validate with activation checks for qrexec PAM files. |
| ACPI shutdown | `qubes-acpi-shutdown-service-type` | Run `acpid` with Qubes event configuration under Shepherd. | Qubes `qvm-shutdown` relies on the guest handling ACPI power-button requests. | Validate with dom0/openQA TemplateVM/AppVM shutdown smoke. |
| Xen and Qubes runtime setup | `one-shot-service`, `%xen-device-setup-command`, `%qubes-runtime-setup-command`, `qubes-sysinit-service-type` | Materialize Xen device nodes, Qubes runtime directories, service environment paths, and run upstream `qubes-sysinit.sh` before dependent services. | Qubes VM agents expect device nodes and runtime paths normally prepared by distro/systemd integration. | Validate with rootfs activation, postinstall diagnostics, and dom0/openQA smoke. |
| QubesDB and qrexec services | `qubes-db-service-type`, `qubes-qrexec-agent-service-type` | Run QubesDB and qrexec through Shepherd with Qubes runtime environment variables and device setup. | Native Guix uses Shepherd; Qubes agents still need Xen device permissions and Qubes runtime paths. | Validate with dom0/openQA qrexec and QubesDB smoke for both variants. |
| qrexec fork server | `qubes-vm-gui` package XDG autostart path and `qubes.WaitForSession` wrapper | Keep upstream's XDG autostart launcher as the owner of `qrexec-fork-server`, and make `qubes.WaitForSession` wait for that server's socket. | `qrexec-fork-server` daemonizes and belongs to the user GUI session readiness path, not root Shepherd supervision. | Validate with dom0/openQA qrexec and session-readiness smoke. |
| GUI agent service | `qubes-gui-agent-service-type` | Start `qubes-gui` only when QubesDB says GUI is enabled, consume `/run/qubes-service-environment`, and preserve Qubes GUI options. | Qubes GUI startup state is communicated through QubesDB and generated service environment rather than Guix desktop session defaults. | Validate basic GUI/appmenu behavior with dom0/openQA; broader GUI usability remains a release gate. |
| meminfo writer | `qubes-meminfo-writer-service-type` | Supervise Qubes `meminfo-writer` through Shepherd, honoring `/run/qubes-service/meminfo-writer` and standard threshold/delay defaults. | Matches Qubes guest-side memory ballooning plumbing without systemd. | Validate the service flag, pidfile, live process, and balloon pressure with Qubes' existing dom0/openQA integration tests. |
| Qubes-managed network uplink | `qubes-network-uplink-service-type` | Bring loopback up, wait for the Qubes-managed interface, and run upstream `setup-ip add`. | AppVM networking should use Qubes-provided network interface setup rather than independent Guix network policy. | Validate AppVM uplink behavior separately from NetVM/ProxyVM ownership, which remains a broader release gate. |
| updates proxy | `qubes-updates-proxy-forwarder-service-type`, Guix update-operation environment, and core agent wrapper | Forward update-operation traffic through Qubes `qubes.UpdatesProxy` without hiding ordinary Guix commands behind a global wrapper; do not implement a separate updater policy. | Keeps network/update behavior inside the Qubes RPC model. Shepherd provides the local TCP listener via `socat`, while the per-connection wrapper follows Qubes' current socket-activated `--use-stdin-socket` command to preserve bidirectional EOF handling. The Guix daemon itself is not forced through `127.0.0.1:8082`, because that listener is only active when Qubes marks the VM as an update client. | Release evidence must include generated proxy configuration plus a real Guix update/download through an Internet-capable Qubes update target. |
| private volume layout | `qubes-mount-dirs-service-type`, `qubes-bind-dirs-service-type`, system `swap-devices` | Use standard `/dev/xvdb -> /rw`, `/rw/home -> /home`, `/rw/usrlocal -> /usr/local`, Qubes bind-dirs, and `/dev/xvdc1` swap. | Matches the standard Qubes template storage model while expressing it declaratively in Guix. | Validate with dom0/openQA AppVM smoke for `/rw`, `/home`, `/usr/local`, persistence, `/dev/xvdb`, `/dev/xvdc1`, and active `/proc/swaps`. |
| Late Qubes setup | `qubes-misc-post-service-type` | Run upstream `misc-post.sh` as a best-effort late service and log failures without aborting Guix boot. | In systemd templates this late unit can fail while leaving the VM usable for qrexec and postinstall; Shepherd boot one-shot failures would otherwise be fatal. | Validate with postinstall behavior and openQA logs for known fatal failures. |

## Review Notes

- The adaptations above should remain small and Guix-specific.  If an upstream
  Qubes release removes the need for one, drop the local adaptation rather than
  carrying it forward.
- Integration testing is delegated to Qubes OS's existing openQA suite, which
  is external to this repository.
- `VALIDATION.md` is the source of truth for which adaptations have live
  TemplateVM/AppVM evidence and which are still only build or rootfs evidence.
